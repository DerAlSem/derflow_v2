## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Замер 27.11.2026, 09:59–11:30 (gmb_v2, хендофф `.claude/handoff/bl-wake-alarm-ztui.md`). Хук отложки подключён там проектно — `.claude/settings.json` → SessionStart → `bl-wake.py`, — а ztui проектный слой хуков не читает: zcode-cli 0.18.0-2 берёт команды только из `~/.zcode/cli/config.json` и плагинов (configured-runner-callback.ts; читателя `.claude/settings` в пакете нет). Итог: в ztui-сессии gmb_v2 (старт 09:59) созревшего не было, хотя кэш 09:44 нёс 14 🟢 — GM-511, GM-790, GM-657.4 и ещё 11.

Вторая причина под ней: ZCode выбрасывает plain stdout хука молча, в контекст идёт только JSON `{"additionalContext": …}` (parseHookStdout). У `waiting.py`, `stale-root.py`, `canon-budget.py` обёртка `emit()` есть, у `bl-wake.py` её нет — одной регистрации в config.json не хватило бы.

Третья — режим хука печатает кэш целиком: 19 566 Б, из них 79 📂 (84%) — прошедшие сроки пересмотра, состояние, а не переход; та же строка на каждом старте, в Claude Code тоже.

Слово владельца 27.11.2026 ≈10:40: «надо настроить будильник в дерфлоу и кеш разбирать».

Границы. Форма 📂 — рабочая, вариант 1 хендоффа: 🟢 и ⚪ всегда, 📂 одной строкой счёта по месяцам, полный список — `--overdue`. Владелец форму не выбирал; альтернативы — дельта в переходе (2), всё целиком (3); разворот к (3) — смена ключа по умолчанию, (2) — отдельная задача. Содержимое кэша gmb_v2 (79 просроченных, 14 созревших, 4 недостижимых) — не эта задача: триаж колонки Backlog отдельной сессией в gmb_v2 по слову владельца. Управление регистрацией zcode-хуков из install.sh не заводится: `~/.zcode/cli/config.json` правится руками (hosts/BRIEF.md:43), как и прежние три записи.
